# AES distribution source and rebuild evidence

This directory supplies the preferred TypeScript source and build inputs for
`@cryptography/aes@0.1.1`, the dependency used by Telegram/GramJS. The npm package
declares `GPL-3.0-or-later`. `GPL-3.0.txt` preserves the full GPL version 3 text;
the package's "or later" declaration is retained in `manifest.json` and in the
unmodified upstream package metadata.

This is an AES-specific provenance record, not a declaration that the complete
ARVIO/Telegram browser bundle or container meets every licence condition.
It does not change ARVIO's project licence or determine the scope of GPL
conditions for the combined browser bundle.

## Source correspondence

The npm publication metadata has no `gitHead`. Its version number alone therefore
does not establish a source revision. Rebuilding the publishing-era source at
`10560e255f20aba057c67a874bdb763e2580ed50` establishes the correspondence:

- All three minified CJS, ES and UMD JavaScript files are byte-identical to the
  integrity-pinned npm tarball.
- The other four JavaScript files and all six declaration files match after
  converting Windows CRLF line endings to LF. No code, comments, identifiers,
  whitespace other than those line endings, or compiler options are normalised.
- The npm tarball also contains a Finder `.DS_Store` file. It is not source or
  executable code and is not regenerated by the build.

`comparison.json` records the observed hashes, tool versions and result from
Node 22.20.0 on Windows. The tarball is checked against the exact SHA-512 integrity
in ARVIO's web lockfile before comparison. The upstream TypeScript, including its
`@cryptography/utils` workspace helper, is included: the helper is bundled in the
published AES JavaScript despite not appearing as a runtime npm dependency.

## Included materials

- `upstream/packages/aes/`: all original TypeScript source, tests, package
  metadata, Rollup configuration, Jest configuration and npm-ignore file.
- `upstream/packages/utils/`: the original workspace helper source, package
  metadata and Rollup configuration required for this build.
- `upstream/scripts/`, `upstream/tsconfig.json`, `upstream/package.json`,
  `upstream/yarn.lock` and `upstream/lerna.json`: original monorepo build inputs.
- `upstream/LICENSE` and `upstream/README.md`: the original monorepo notices.
  Its root Apache licence is retained without overriding the AES npm package's
  specific GPL declaration or making a new licence interpretation.
- `toolchain/package.json`, `toolchain/package-lock.json` and `toolchain/.npmrc`:
  an isolated, pinned subset of the historical build tools. These tools are for
  rebuilding this old release, not new runtime dependencies of ARVIO. The original
  monorepo lockfile is also retained. Modern npm's peer-dependency check is
  bypassed to reproduce the old Yarn tool combination; package install scripts
  are disabled. `aes-worker-limit.cjs` bounds the old minifier's worker pool and
  changes scheduling only.
- `manifest.json`: immutable upstream revision, SHA-256 source hashes, npm
  tarball integrity, component licence declaration and recorded build versions.

The imported `.npmignore` and AES `README.md` had no final newline upstream. The
text-file import adds one trailing LF to each; these two non-code normalisations
are explicitly recorded in the manifest. All remaining snapshot files match
the downloaded upstream bytes.

## Verify and rebuild

From the ARVIO repository root:

```sh
node web/scripts/aes-verify-source.mjs
node --test web/distribution-sources/aes/aes-source.test.mjs
npm ci --prefix web/distribution-sources/aes/toolchain --cache web/distribution-sources/aes/toolchain/.npm-cache
node web/scripts/aes-rebuild.mjs
```

The first two commands work offline and do not require installed web dependencies.
The rebuild downloads the integrity-pinned npm tarball for comparison and requires
the pinned verification toolchain. It builds the workspace helper, then AES using
their original Rollup configurations. Source files are copied into a fresh
`rebuild-output/run-*` directory; the supplied snapshot is never rewritten.
The report fails if any JavaScript/declaration differs beyond CRLF line endings,
or any minified format is not byte-identical. Output directories, npm caches and
installed verification tools are ignored and must not be packaged as source.

Successful rebuilds also write the canonical
`rebuild-output/latest-comparison.json`. After the normal Next build, run
`node web/scripts/aes-package-source.mjs` from the repository root (or
`node scripts/aes-package-source.mjs` from `web/`). It creates a clean
`.next/distribution-sources/aes` staging folder using an explicit material
allow-list. That folder contains the rebuildable relative layout under
`source-root/`, the matching web lockfile/project license, a fresh
`verified-comparison.json`, source hashes, and concise source directions. It
excludes installed tools, caches and scratch output. Packaging fails if its
destination already exists; normal clean Next builds supply a fresh destination.

For distribution, preserve this directory's tracked source/materials **and**
`web/scripts/aes-rebuild.mjs` and `web/scripts/aes-verify-source.mjs` in their
relative layout, or include the matching repository snapshot alongside the
component source bundle. The image/download notice should tell recipients where
to obtain these materials. Browser-accessible notice/source directions and the
combined-work licence decision belong to the distribution integration, not this
component verification script.
